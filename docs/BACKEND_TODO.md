## Decisions

- 2026-10-19 (latency targets tightened the same day), **Capacity target (acceptance for the backend, §14)**: at least **1,000 TPS peak** and **50 million SMS a day** (about 580 TPS on average). The Elixir backend is accepted only when a load test against the SMPP simulator shows all of the following:
  - **1,000 TPS sustained for 1 hour**, and bursts above it absorbed by the per-trunk queues, with every message billed and receipted.
  - **50 million messages in 24 hours** with their delivery receipts.
  - **No message or EDR lost** when a service restarts mid-test (durable queue between services), and the EDR count equal to the messages accepted.
  - **submit_sm_resp within 50 ms (p99)** on the switch, and **EDRs visible in reports and Live analytics within 2 s** (p99; EDRs are batch-inserted every second).
  - The GUI stays fast at that volume (p95, over 30 days of EDRs, about 1.5 billion rows): **lists, filters and record pages under 300 ms**, **today's reports and Live analytics under 500 ms**, reports over months under 2 s.
  - Sizing to plan for: about 8–10 GB of compressed EDRs a day in ClickHouse (measured on the fake data: ~8.4 GB per 50 million rows), so retention × that, plus replicas; delivery receipts written as updates to the same EDR.
  - **Retention (decided 2026-10-19, spec §14.3)**: EDRs online 12 months, then a daily job moves the oldest day to compressed archive storage kept for the legal period (minimum 7 years, §13.29), restorable on request; hourly / daily summaries, invoices, SOAs and payments stay online for good. *Backend*: ClickHouse TTL `MOVE TO VOLUME 'archive'` (or export to object storage) after 12 months, restore job, "partly archived" flag on EDR search. *GUI later*: restore request screen and the archived-period notice on EDR search / download.
  - **Production servers (proposal, to confirm with the load test):**
    - Switch and API (Elixir): 2 servers, each 16 vCPU, 32 GB RAM, 200 GB NVMe for the system plus 2 TB for the 60-day traffic recording (PCAP Trace, ~1–1.2 TB) (either carries the full load alone).
    - ClickHouse (EDRs): 2 servers (replicas), each 32 vCPU, 128 GB RAM, 8 TB NVMe (12 months at ~8–10 GB/day plus merge headroom), or 2 TB NVMe for 3 hot months plus cheaper disk / object storage for older months.
    - PostgreSQL (config, billing): primary + standby, each 8–16 vCPU, 64 GB RAM, 1 TB NVMe.
    - Queue and live counters (NATS JetStream or Kafka, Redis): 3 servers, each 8 vCPU, 16 GB RAM, 500 GB NVMe (3 days of messages for replay).
    - Network 1 Gbps outside, 10 Gbps between the database servers; backups off-site, at least the size of ClickHouse + PostgreSQL.
    - Smallest single-server setup (no redundancy, a failure stops traffic): 32 cores, 128 GB RAM, 2 × 8 TB NVMe in RAID 1, plus an off-site backup.

## App shell notes (build step 3)

What the Phoenix backend must match so the screens need no change:

- **List queries** (`POST /{list}/query`): the mock's engine in `mock/src/lists/engine.ts` is the reference for semantics. Text operators are case-insensitive (`ILIKE`, `lower()`); `like` uses `%` / `_` with backslash escape; `regex` is POSIX case-insensitive (`~*`), and a pattern PostgreSQL rejects answers 400; negative operators (`neq`, `not_like`, `not_in`) keep rows whose value is empty; every sort ends with the record ID as tie-breaker; quick search matches the list's text columns. The mock's cursor is an offset; the backend may use keyset paging as long as the cursor stays opaque.
- **Field catalogues** (`GET /meta/lists/{list}/fields`) drive the grid's column filters and the filter builder; adding a field to a list needs no screen change.
- **Undo** (`POST /changes/{id}/undo`): restores only the fields the change touched; a later change by another user to the same record and field (not itself undone) is a conflict; undo of `create` archives the record, undo of `delete` restores it; the undo is a new change with `undo_of_id`; a change can be undone once (400 afterwards); undoing someone else's change needs the `undo_others` permission (403 otherwise).
- **Live socket**: `/socket/websocket?vsn=2.0.0`, Phoenix Channels V2 frames. The shell joins `live:tps` (tick once a second) and `alerts:<userId>` (incidents). The browser opens one socket in the main window and relays it to tabs dragged into other windows.
- **Workspace**: the GUI saves the open tabs (path, title, pinned) about a second after each change; page state (filters, sort, columns) is inside each tab's path.

## Enterprise and trunk notes (build step 4.1)

- **Saves** answer `{record, change}`: the saved record plus the change it recorded (null when nothing differed), so the screen shows "Saved · change #n" with Undo (§13.10). The change diff is field-level with API field paths (`address.city`, `contacts.finance.emails`, `billing.customer.creditLimit`, `rateTableIds`, `rules.translation`, `accountManagers`, `archived`). Undo must be able to put each of these back; the mock's appliers are `applyEnterpriseField` (`mock/src/api/enterprises.ts`) and `applyTrunkField` (`mock/src/api/trunks.ts`).
- **Passwords** are write-only: never returned (`passwordSet` instead), never written to the change log (the diff says `(changed)`), so undo can't restore an old password (§13.22).
- **Reserved names** (§13.29): enterprise names and trunk names are unique per kind including archived records, and customer trunk usernames (our SMPP system_id) are unique including archived ones. Vendor trunk usernames are the vendor's credentials and may repeat.
- **Safe delete** blockers: enterprise = live binds, unpaid or draft invoices, non-zero customer or vendor balance, open disputes (partner invoices in mismatch / pending); trunk = live binds. Info items: trunks archived with the enterprise, route rules, rate tables, rules attached directly, traffic in the last 30 days (the mock answers `count: null`; the backend reads the EDR store). An override needs an administrator and a written reason, and the reason is the change note. Archiving an enterprise archives its live trunks in the same change; restore (admin only) brings back the trunks archived with it.
- **Balance** (§5.3): customer = opening balance + invoice usage charges − credits + debits; vendor = opening balance + accepted / matched partner invoices − payments (debits) + credits. Excluded payments still count (§13.33).
- **Handover** (§13.30): effective now or later, never in the past; a new handover replaces a scheduled one that hasn't started; the current AM is the history row covering now. The mock applies due handovers when the record is read; the backend should run this as a job at the effective time. Undo after the effective time should need a manager (not enforced by the mock yet).
- **Trunk Rules tab** (§13.2): shows every translation (and, for customer trunks, HLR) rule that reaches the trunk, with where it comes from (the trunk, its enterprise, its category, all trunks), in run order (same as `rulesForTrunk`). Saving a list gives the listed rules positions 1..n; other positioned rules follow. Detach removes only the rule's direct trunk target.
- **Vendor trunks** get their own buy rate table on create (vendor billing currency, else USD) (§13.12). A trunk can't move to another enterprise; clone it instead.
- **Docs** are stored in the database in this phase (max 10 MB, base64 upload); the backend may use object storage behind the same endpoints.

## Rate Manager notes (build step 4.2)

- **Versions, never edits in place** (§6.2, §13.29): a new rate from `effectiveFrom` closes the version valid then (sets `valid_to`) and opens a new one; versions starting at or after that date are replaced. `effectiveFrom` can't be in the past (one minute of clock skew allowed), so traffic already sent keeps its rate (§13.32). Closing a scheduled line withdraws it and the version before it runs on as long as the withdrawn one would have. Blocking flags the line in place.
- **Change log** for rate edits: entity `rate_table`, record id = the table, one diff entry per touched line with field `line` and full line snapshots before/after (null = the line didn't exist). Undo deletes, then updates, then inserts, so no two versions of a destination overlap at any step (the exclusion constraints stay on). A line edited twice in one batch collapses to its first and last state. An undo change lists the same record ids as the change it undoes, and its entries run in reverse order.
- **Notice period** (§13.14): an increase on a customer table that starts sooner than the longest `rate_notice_days` among the clients using the table answers 409 with the breaches; `acceptNoticeBreach` applies it and the change note says so. New destinations and decreases are never a breach. Vendor tables have no check.
- **Best buy** = the cheapest rate valid now for the same MCCMNC and product category among live, active vendor trunks, without sender-ID or blocked lines, converted through the latest exchange rate (`best_buy_rates`). The backend should keep it current on every vendor rate change and when scheduled rates start; the mock refreshes it after vendor edits and every 5 minutes (about 3 s at full volume). `rate_table_stats` holds the per-table counts the list sorts on: refreshed for one table after its edits and for all after a best-buy refresh.
- **Traffic figures** (avg margin weighted by today's volume, revenue or cost today) come from the EDR store: customer tables by `c_rate_table_id`, vendor tables by `v_rate_table_id`, today in the platform time zone. They are null when the EDR store doesn't answer, and not filterable or sortable (no operators in the field catalogue).
- **Database settings**: integer list filters compare as `bigint` so they use the ID indexes (a `numeric` cast made `rateTableId = n` scan all 1.4 M lines), and JIT is off for API connections (it added 2 s of compile time to list queries with many small subqueries).
- Not in this step: rate import wizard and rate notices to clients (§12.1, §13.13; the buttons show disabled), Bulk rating opens the bulk workspace (§13.11, build step 5).

## Route Rules notes (build step 4.3)

- **Saving** (§6.3, §13.10): `PUT /route-rules/{id}` takes the whole rule; the change records only the fields that differ (vendors and whitelists as whole lists), so undo restores them. A save that changes only `status` is logged as `enable` / `disable`. The GUI saves one condition or one vendor edit at a time, so each is one undoable change.
- **Drafts**: a rule may be saved off (inactive) without vendors, so a new rule can be built step by step in the detail panel. A static rule needs at least one non-backup vendor to be on: `PUT` with `status: active` answers 400 on `/vendors`, and bulk `enable` answers 400 naming the rules. New rules from the GUI start off.
- **Evaluation order** (mock `src/routing/evaluate.ts`, for the Elixir switch to match): status and start/stop time, then category, customer trunk, destination (codes, 3-digit code = whole country, plus the MCCMNC regex), sender / receiver / content patterns and lists, HLR ported, TPS (§13.8, with tolerance for `=`), revenue (§13.9; per message from the customer rate, accumulated over its period and scope), joined by `matchMode` all / any. Then vendor choice: number whitelist → warm-up threshold → hunt policy (percentage split, top down, round robin) for static rules, cheapest first for dynamic, quality score for QBR; vendors leaving less than `margin` (flat) or the revenue condition's minimum margin are skipped, and so are vendors at `skipVendorAtTpsPct` of their TPS. The simulator tries active rules by priority (then ID) and stops at the first match unless Continue routing is YES.
- **Traffic figures** (§13.27): the grid columns read `route_rule_traffic`, refreshed from the EDR store every 60 s for the five windows (the window ends at the latest EDR, so fake data with a fixed time range still shows figures). ASR = submits accepted ÷ attempts, DLR = delivered ÷ accepted, margin = revenue − cost in the platform currency (each EDR's `*_sys` amounts are in its business company's base currency, so the mock converts them per company at query time). The backend should feed this from the live counters (Redis) instead of a periodic query. Without the EDR store the figures are null and the traffic endpoint answers `available: false`.
- **Bulk** (§13.11): one change for all rules; replace vendor swaps the trunk on every level and in whitelists. Archive is the safe delete (§13.29); a rule has no blocking dependencies.
- Not in this step: Route map, LCR, Re-rating, Rate lookup and Simulator as their own pages (build steps 4.4 and 5; the header Simulate dialog already runs `POST /route-rules/simulate`), and the predictive route costing panel while editing vendors (the Test section shows cost and margin per candidate).

## Rate Lookup notes (build step 4.4)

- **Which line counts** (§6.2, §5.4): for a network, a table's line for that MCCMNC, else its country line ("all networks"); for a whole country, its country line, else its cheapest network line (shown with `matchedCode` and a `*` in the GUI). Sender-ID lines count only when `senderId` is given. Blocked lines never count. A client's rate is the first of its trunk's rate tables (by position) that has a line, as the switch rates traffic.

A vendor is "routed" when it is the routed vendor for at least one client. The mock routes in bulk (rules pre-filtered by destination, a yes/no match test, sorted least-cost pools cached per destination, one evaluation per distinct trunk category / sell rate / sender), about 0.1 s for a destination with 400 clients. - **Traffic figures**: vendor 24 h and client 7 days by `c_mccmnc` (the country: every network of it), ending at the latest EDR like the route-rule windows; null without the EDR store.
- **Highlights**: below cost (a client's sell under the best cost), cheaper than routed (the best vendor is cheaper than a client's routed vendor), expiring soon (a rate ends within 14 days with no version after it; a line closed by a scheduled change is not expiring), single vendor. Filtering on highlights computes every destination of the lookup first, so it is limited to 1,000 destinations (the backend may precompute these flags).
- **Matrix columns**: the 60 trunks covering most destinations of the lookup after filters (`columnsTruncated` when more exist); rows page 50 at a time. Timings at full volume (Australia + Germany, 59 destinations): 0.8–1.9 s per page depending on the view (routing makes vendor costs and margin the slowest); easy mode 0.08–0.6 s.

## Migration Center notes (build step 5.20, §13.22)

- **Export package** (`mock/src/migration/package.ts`): one file, `SMSPKG1` + JSON header + AES-256-GCM ciphertext of gzip(frames) + 16-byte tag. The key comes from the export password through scrypt (N 16384, r 8, p 1); the password is never stored.
  - Frames: `manifest.json` (record counts per entity with sensitivity, link counts), then one CSV per table via `COPY … TO STDOUT CSV HEADER`.
  - 24 tables from countries to transactions. Archived records stay out, and so do child rows of archived parents, so every link in the package resolves.
  - Rate lines: current and future, all with history, or none. A full package at generated volume (1.4 M rate lines) takes about 10 s and is about 21 MB.
  - Levels: connection details (System IDs, hosts, IPs, ports) only with "include credentials"; passwords only with "with passwords" as well. Our own users' password hashes and 2FA secrets are never exported.
- **Credentials safeguard**: an export or import that includes credentials needs an administrator with 2FA on and a valid code. The call is in the audit trail, and the other admins get a `credential_transfer` e-mail (Email Logs).
  - Downloads go through a link that works once and expires after 15 minutes. A package with credentials needs another 2FA code for the link.
- **Import** (`mock/src/migration/importer.ts`): one CSV per entity, in dependency order: users, enterprises (and contacts), customer trunks, vendor trunks, rate tables, rate lines, route rules, opening balances.
  - Columns: template field names or labels, or a saved mapping. The reference platform's grid column names are ready as mappings.
  - Matching: the old ID (`migration_refs`, per source system), else the natural key (username, name, name and kind). Per entity: skip (default), update the changed columns, or create anyway.
  - Records of the same import link to each other by old ID or name.
  - The dry run writes nothing. It counts new / update / skip / errors against the rows in the file and the records in the system, and lists problems by row (at most 500, shared between entities).
  - A system-to-system import reads a package (export number and password) and turns its tables into the templates, with the old IDs as external IDs.
- **Apply**: runs the same plan again in one transaction. If the counts differ from the dry run, nothing is written, the new report is stored and the answer is 409.
  - It is one change in History, entity type `migration`, change type `import`. Each entry has `table`, and field `*` (created) or `row` (changed columns with before and after).
  - Undo rolls the whole import back: created records are archived, changed columns go back. The import then shows "Rolled back". Rate lines are reached through their archived tables.
- **Go-live**: trunks are created inactive by default. Activate per partner or all at once; each activation is one undoable change (change type `enable`).
- **Rules the import keeps**:
  - Rate lines go only into rate tables the same import creates. Lines of existing tables are skipped with one warning; use the Rate Manager upload for those.
  - Versions of a destination are chained (each ends where the next starts).
  - Opening balances become adjustment transactions, only for partners the import creates. Partners already in the system keep their balance.
  - Trunks without credentials in the file get a placeholder System ID or host, with a warning.
  - Usernames are unique across archived users too.
- *Fixed in this step: a Fastify reply is thenable, so a helper that sends a problem must not return the reply through `await`. `refuseMasked` (§13.17) and the number-list `liveList` now return a boolean or null. Before, a refused call could carry on after its 403 or 400.*
- *Not in this step: EDR import (EDRs stay in the old platform's store and link through `migration_refs`); translation, HLR and number-list import (they come over in the package but have no template yet); invoices and payments history beyond opening balances.*

## Cleanup Center notes (build step 5.19, §13.19, §13.20)

- **Scan** (`mock/src/api/cleanup.ts`): about 1 s, at start and then nightly, or with Scan now. Each finding has a fingerprint (kind + records), so a rescan updates the same finding.
  - New findings are open. Ignored ones stay ignored.
  - Open findings no longer found become resolved. Applied findings found again reopen.
- **What it finds**:
  - Route rules:
    - Unused: 0 messages in the last N days (default 30), from the rule traffic cache.
    - Expired: the stop time passed more than 7 days ago.
    - Identical: same conditions and routing, whatever the name and priority.
    - Near-duplicate: they differ only in their client trunks.
    - Shadowed: an earlier rule with the same conditions and "stop" takes all its traffic.
    - Conflicting: same priority and conditions, other vendors.
    - Broken: a deleted or inactive vendor trunk in its list.
  - Translation and HLR rules on no trunk; number lists no rule uses.
  - Customer rate tables on no trunk, and rate tables with identical current lines.
  - Trunks with no traffic in N days (inactive ones: archive; active ones: deactivate).
  - Enterprises without an active trunk or traffic for N days (dormant), and the same company twice (name apart from punctuation and legal form, or the same VAT number).
  - Users not signed in for N days.
- **Actions**:
  - Merge: identical rules keep the first and archive the rest; near-duplicates give the first all client trunks and archive the rest.
  - Delete (archive, restorable).
  - Deactivate.
  - Reassign: remove the dead vendors when working ones remain.
  - Reorder: the later of two conflicting rules moves one priority lower; the routing result is unchanged.
  - Review: nothing automatic, e.g. duplicate enterprises or rate-table copies that are on trunks.
  - Ignore needs a reason.
- **Replay**: before applying route-rule cleanups, the 300 busiest client trunk and destination pairs of the last 24 hours go through today's rules and through the rules as they would be. Every pair whose vendor changes is listed. About 4 s.
- **Apply**: one or many findings (or one action for all) are one change in History, entity type `cleanup`, with each entry naming its record type. Undo puts everything back and reopens the findings; undoing the undo applies them again.
  - With "approval required", a non-administrator's cleanup waits until an administrator approves it.
- **Weekly summary**: an e-mail (`cleanup_summary`, Email Logs) to the rules owners when findings are open, at most once a week.
- **Badges**: Route Rules, Translation rules and HLR rules show "Cleanup n", which opens the Cleanup Center filtered on their kinds.
- **Duplicate warning on save**: the enterprise form (same name, VAT number or e-mail domain) and a route rule's Conditions (same conditions and vendors, or same conditions with other vendors).
- *The fixture adds redundancy so every kind shows up:*
  - *6 identical rules plus 2 pairs, 3 near-duplicates, 2 conflicts and 2 shadowed rules;*
  - *3 duplicate enterprises;*
  - *an identical rate table.*
- *Not in this step (§13.20 follow-ups): rate-line redundancy (duplicates, overlaps, lines equal to the country line); merging enterprises or rate tables that are on trunks; "apply settings template" for trunks; unused file / e-mail templates, saved views and scheduled reports; templates and naming patterns to prevent copies; the 90-day purge of archived records; old IDs pointing to the merged record.*

## LCR notes (build step 5.16, §13.23)

- **LCR table** (`mock/src/api/lcr.ts`, ranking in `mock/src/lcr/rank.ts`): every vendor trunk with a generic, unblocked rate for the destination at the point in time. A network falls back to its country's "all networks" line, as in Rate Lookup.
  - Each row shows cost in the platform currency, the rate in its own currency, since when, and the next scheduled rate.
  - Quality is the vendor's QBR stats for the destination (overrides win) for ASR, DLR, delay and sample. TPS now comes from the live simulator, against the trunk's limit (95 % or more counts as at the limit).
  - "Routed now" is how many client trunks today's rules send to that vendor.
  - Inactive trunks are listed and left out.
  - *Past points in time use past rates but today's quality and routing.*
- **Ranking**: by cost; with the quality-weighted score, by a 0–100 blend of cost and delay (scaled within the destination's vendors, lower is better) with ASR and DLR (unknown counts as 50). The weights are editable.
  - Ties go to the better DLR or the lower cost (tie-breaker).
  - Unknown quality is not held against a vendor in the minimum ASR / DLR / delay checks, because new vendors have no traffic yet.
- **LCR profiles**: include / exclude vendor trunks, allowed tiers, minimum ASR / DLR, maximum delay and cost, number of vendors (1–10), top-down or percentage split (shares per position adding up to 100), tie-breaker, leave out vendors at their TPS limit, quality-weighted score.
  - A route rule of type Least cost may carry one (`lcrProfileId`). The evaluator then filters, orders and splits the vendors with the profile (decided by "lcr"). Without a profile it is the cheapest vendors in scope, as before.
  - Profiles are undoable records; deleting one is blocked while rules use it.
  - "Apply LCR": the Route Rules Bulk edit "Apply LCR profile…" makes the selected rules Least cost with the profile, as one undoable change. The LCR page's "Apply to route rules" opens Route Rules filtered on the destination.
- **What-if**: remove vendors, or give a vendor a new cost (an offer from a vendor without a rate here counts too). The answer is the new ranking with each vendor's former rank.
  - It also gives the client trunks selling the destination whose routed vendor changes under today's rules (Least cost rules follow the new costs), and the cost and margin change on their last 7 days of messages (EDRs).
- **Client view**: per client trunk and destination, for one client or one account manager's clients: the sell rate (first rate table with a line), the three cheapest eligible vendors (the profile applies), the margin at each position, and below-cost lines.
  - Computed in one SQL pass and cached a minute; filtered, sorted and paged on the server.
  - About 2.6 s for an account manager with 54,000 lines.
- **Change alerts**: every 15 minutes the cheapest live vendor and cost per destination is compared with the last check. A change of top vendor, and a cheapest-cost move beyond the threshold (default 5 %), are recorded in LCR › Changes, linked to a market move on the same destination (§13.14).
  - On the first start, the last 7 days are replayed day by day to give a history.
  - *As decided for RNs and market moves, no pop-up through the alert engine.*
- **Actions**: Export (CSV of the table on screen); "Price clients from LCR" opens Bulk rating for the destination (cost + margin action, §13.11).
  - *Not in this step: scheduling an LCR report by e-mail. The Scheduled reports page (§10) can carry it once an LCR report type is agreed.*

## Market move notes (build step 5.15, §13.14)

- **Detection** (`mock/src/api/marketMoves.ts`, rules in `mock/src/market/detect.ts`) runs 20 s after start, every 15 minutes, and a minute after any vendor rate change (Rate Manager edits, Bulk rating, accepted RNs §13.13, undo). It takes about 7 s at full volume.
  - **Top vendors of a destination**: the cheapest N (default 3) live vendor trunks by the rate valid now (USD, latest exchange rates), plus every Tier 1 vendor's trunk with a rate there (setting).
  - **Changes**: a new version of a generic, unblocked vendor line that replaces the previous one (`valid_to = valid_from`). It must be within the look-back (default 30 days, scheduled future dates included) and move by at least the minimum % (default 3).
  - **Move**: at least N (default 2) top vendors move in the same direction with effective dates within the window (default 7 days); the latest change per vendor counts.
  - **Recorded** once per destination, direction and first date. Re-scans update its figures and keep its state; snoozes end on their date. Moves dated before the look-back that nobody acted on become Expired. Destinations no client table sells are not recorded.
- **Market cost** before and after = the cheapest top-vendor rate before and after the move's changes. A move among expensive vendors therefore leaves the market cost (and the suggestions) unchanged.
- **Affected clients**: customer tables used by a live trunk with a current generic line for the destination. Each shows the sell rate, the margin against the old and the new market cost, 7-day volume (EDRs), the longest notice period of the clients using the table, and a suggested rate. The suggestion is the new cost plus the client's current margin, or the target margin (setting) when higher, from the move's last date or the end of the notice period.
  - "Update rates" opens Bulk rating with the chosen tables' suggestions as `overrides` (action `none`), so they can be reviewed and changed before applying.
  - After applying, the move is marked handled with the change number.
  - "Reroute…" on a vendor that moved opens Route Rules filtered on it; the card names the top vendors that did not move.
- **Urgent**: an increase of at least the urgent % (default 10) starting within the urgent days (default 7). Urgent moves are counted on the dashboard card. *No pop-up through the alert engine, by analogy with the RN decision of 2026-10-17; say if you want one.*
- **Account managers**: each move keeps the account managers of the affected clients (`affected_am_ids`). The list filters on them (account manager picker), and the dashboard card counts "mine". *Hiding other AMs' moves by default is still open after AM visibility (§13.17, step 5.17 masks their names).*
- **Daily digest**: one e-mail per account manager at the digest hour (default 07:00 UTC), with the moves not yet in a digest. It is logged in Email Logs as `daily_report`; "Send digest now" sends it at once.
- **Auto-apply rules** (per client or product category): follow increases, or decreases too, to keep a minimum margin. When a new move is recorded, each covered table whose margin at the new cost falls below the minimum is re-priced at the new cost / (1 − minimum), from the move's last date or the client's notice, whichever is later. That is one undoable change per table, logged on the move. Rules and settings are not in the change history (they are settings, not rates).
- **Volume**: with the default settings, the fake data gives about 2,400 open moves in 30 days. Typically 2 of about 20 top vendors move, because 35 vendors are Tier 1 and price every destination. Without Tier 1 vendors it gives about 100 (2 of the 3 cheapest). Decided 2026-10-17 (team): Tier 1 vendors are top vendors, so the default stays on.
- *Not in this step*: "Notify clients" goes through the normal rate notification e-mail (Switch › Notifications, §8) after the rates change; it is not started from here.

## Incoming RN notes (build step 5.14, §13.13 A, §13.32)

- **Intake** (`mock/src/api/rn.ts`, sheet reader `mock/src/rn/parse.ts`): one call per incoming e-mail or upload. In this phase the e-mail is fake: the page's "Simulate an e-mail" or a test posts it. The backend polls the shared rates mailbox (§13.13 "one general email setup") and calls the same logic.
  - **Finding the trunk**: the vendor trunk's username (SMPP system_id) or trunk name in the subject, then the file name, then the body. The sender's address narrows it to enterprises whose contact e-mails match (address or domain). If that enterprise has a single live trunk, that trunk is used. Nothing is guessed between two trunks: the RN is **Unmatched** and waits for "Assign to trunk".

- **Check (§13.32)** runs at intake, on "Re-check", on assign, and at start for seeded pending RNs.
  - Each line is compared with the trunk's rate valid now (same sender ID): New, Increase, Decrease, Unchanged, Closed.
  - Traffic on the vendor trunk and destination (`v_trunk_id`, `v_mccmnc`) comes from EDRs for the last 1 h, 24 h and 7 days. A line is **live** when the configured window (default 24 h) has at least the minimum messages (default 1). **Flagged** = an increase or a close on live traffic.

  - **Back-dated**: stated before receipt. The line shows the messages sent between the stated date and receipt, and their cost at the old rate.

The stated date stays on the line, and the Successful or Rejected reply names the dates actually applied. EDRs are never re-rated; a back-dated agreement goes through a manual Re-rating request (§6.3).

Accepting loads the lines through the same code as Rate Manager edits and saves ONE undoable change on the vendor rate table (§13.10); undoing it puts the rates back, but the RN keeps its decision. The RN stays Pending review while lines are pending; then it becomes Accepted, Rejected or Partly accepted.

Each kind is sent at once, drafted for confirmation (edit, then Send), or switched off, per vendor or by the global default. Replies go to the sender plus the vendor's extra addresses; if there is no sender (an upload), to the vendor's rates contact. Every reply is logged in Email Logs and kept with the RN.

## Bulk rating notes (§13.11, rating part)

- **Where**: Rates › Bulk rating (`/rates/bulk`). With no destination, the job covers every current line of the tables. The lines are the ones valid now, sender-ID lines included. "Also add destinations a table lacks" adds a generic line (no sender ID) for each listed destination the table has no rate for; this works for a fixed rate and for cost + margin only.

- **Notice periods (§13.14)**: an increase on a table whose clients have a notice period is flagged when it starts sooner. With "Respect notice periods" (the default), the increase moves to the end of the longest notice period of the clients using the table. Rows can be excluded one by one or all below-cost / notice-breach rows at once. The impact cards (Step 4) are recalculated from the edited rows: counts, and 7-day revenue and margin change in the platform currency (`toPlatform` per row).
- **Apply (Step 5)** writes every table in one transaction, through the same code as one table's edits (new versions from the effective date, never in the past, scheduled versions replaced). - **7-day traffic** comes from EDRs (`c_rate_table_id`, `c_mccmnc`, customer trunks of the tables), billable messages × rate difference. Sender-ID lines show no traffic, because EDRs don't carry the sender-ID line. Vendor tables show no traffic impact.

State lives in PostgreSQL (`incidents`), so acknowledge and snooze from any tab take effect for everyone.

Bind status reads `trunk_binds` (offline = down; stopped is deliberate and does not alert). A trunk without ASR / DLR history counts for volume only. The minimum sample is the number of messages behind the metric.

  - Country, MCCMNC, sender ID and product category scopes are evaluated on all traffic, because the simulator does not split traffic by destination or sender. The backend evaluates them on the matching traffic.
  - Teams (§13.18) are not a notify target yet.

## Observation Deck notes (build step 5.9)

- **EDR Search on ClickHouse.** The list grammar (§13.25) is compiled to ClickHouse SQL (`mock/src/lists/chEngine.ts`). EDRs carry IDs only, so filters on enterprise, trunk, HLR provider and product category names run on PostgreSQL first and apply as ID lists (`neq` / `not like` / `not in` become `NOT IN`; empty vendor = not routed). Sorting by a name uses `transform()` over the names. A page is read in two steps, first the IDs of the page in sort order, then the full rows of those IDs, because reading every column before sorting is about 30 times slower (6 s against 0.2 s on 5.2 M rows). The backend should keep this pattern, or a projection ordered by start time. Totals are exact (`count()`), all pages answer in under 0.6 s at full volume.
- **Page filters.** From / To Date (UTC) and Final are conditions on `startTime` and `isFinalAttempt`; Customer / Vendor Msg IDs take comma-separated lists (`in`). Every other §9.1 filter is a column filter or the builder: Cause Code and Message Status are enum filters with the §2 lists, Type MO / MT, HLR error code, enterprise / trunk / MCCMNC on both legs. The EDR Template picker sets the grid's columns.
- **Failed EDRs** = attempts with no vendor leg that were not submitted (`v_trunk_id = 0 AND is_submit_success = 0`), about 392,000 in the generated month (invalid destination, submit failed). The backend may keep these in their own table.
- **Trouble Ticket**: vendor tickets go to the chosen vendor trunk's enterprise, customer tickets to the one customer of the selected EDRs (EDRs of several customers are refused). Recipients are the Technical contacts, then Commercial. The chosen EDR columns go in the body as a table and as a CSV attachment, plus an optional file. The ticket is logged in Email Logs (type trouble_ticket). There are two fake templates (8 and 9).
- **EDR Repush** re-sends final attempts that were not delivered: each becomes a new attempt (attempt number + 1, the new vendor trunk, `repush_request_id`), and the old attempt stops being final (an `ALTER TABLE … UPDATE` in the mock). Delivered or non-final EDRs are counted as skipped. In the mock the outcome is random (about 80 % delivered), the new attempt is dated two minutes after the old one (so the generated EDR period does not move) and the rate and cost are copied from it. The backend sends through the switch and prices the new attempt at the new vendor's rate. The 24 seeded repush requests have no EDRs behind them.
- **EDR / Failed EDR downloads** run one at a time in the background. The job counts the rows first (more than 1,000,000, or 1,048,575 for XLSX, fails with a message), then streams ClickHouse `CSVWithNames` or `JSONCompactEachRow` into a CSV or Excel 2003 XML file, with names resolved and the column labels as the header. Progress updates every second, and Cancel aborts the stream. Seeded downloads have no file; they are built again from the stored request when downloaded.
- **EDR Template** got its own page (`/monitoring/edr-templates`, §9.2) and is used by EDR Search, downloads and trouble tickets. Deleting one does not change downloads already requested; they keep their columns.
- **Network Status**: in this phase the mock plays the switch. It keeps `trunk_binds` and `bind_sessions` for every live trunk. TPS starts from each trunk's 7-day EDR average and moves every 10 s; customer binds drop and come back now and then; vendor queues grow while a vendor is offline. Stop unbinds a vendor (its queue is re-routed) or kicks a customer's sessions; stopped trunks stay down until Start. Start binds a vendor at its maximum connections, or accepts the customer's binds again (the customer reconnects about 5 s later). The sessions panel shows where receipts go back (§13.1). The backend fills these from the switch's live state.
- **Signaling Deck and PCAP Trace** are one page (§13.20, redundancy removal): a capture stops at Max Duration, Max File Size or Stop, and at most 3 run at a time. The file is a valid libpcap trace (Ethernet, IPv4 or IPv6, TCP with checksums) of fake SMPP traffic between the filtered client and the switch on port 2775: submit_sm / resp, deliver_sm receipts / resp and enquire_link. It is built from the capture ID, so a file is the same every time, and it opens in Wireshark. Addresses are documentation ranges or the trunks' fake IPs.
- **Route Simulator** runs the customer trunk's translation rules and HLR rule (§13.2), finds the destination (or uses the MCCMNC typed in), the customer rate, the route rules in order and the chosen vendor with cost and margin, and says why a message would be rejected (blocked by a translation or route rule, unknown destination, no customer rate, no vendor). The live counter shows coding, characters (GSM extension characters count twice), bits per character, SMS per message and bytes. In the mock, Test SMS only answers with a message ID and a simulated outcome: nothing is sent and no EDR is written.
- **Network Diagnosis** answers with simulated output (ping, traceroute, MTR, telnet) that is the same for the same input. Host names "resolve" to 203.0.113.x without asking DNS. The mock never sends a packet. The backend runs the tools on the switch host, with the destination and source checked as an IP address or host name.

## HLR notes (build step 5.4)

- **Schema (migration 014)**: `hlr_providers` gains `extra_headers`, `post_data`, `response_mapping` (jsonb with the §6.5 captions) and `updated_by_id`; new `hlr_provider_rates` (price per live lookup per MCCMNC code, unique per provider among live rows; a country's "all networks" code prices the whole country unless a network has its own row; no row = `default_rate`), `hlr_provider_stats` (last 24 h per provider, refreshed every 5 minutes from the EDR store) and `hlr_policies` (`entries` jsonb). `hlr_rules` gains `insert_at`. Route rule `hlr_action` now stores `policy_id`; the 46 seeded actions point at policy 1 "Default".
- **Live status**: inactive when switched off; down when success < 50 %; slow when the average response is over 80 % of the timeout; else up. The generated EDRs mark every lookup accomplished and carry no response time, so the **mock simulates a fixed health profile per provider** (success factor, response time as a share of the timeout). The backend measures both on the real traffic.
- **Policies**: the entry for a number is its network's code, else its country's MCC, else the catch-all; no entry = no lookup. "In order" tries the providers as listed and the next on error or timeout; "auto" puts the providers meeting the minimum success rate first, cheapest first, then the others by price. Success per destination comes from the last 7 days of EDRs (at least 20 live lookups), else the provider's 24-hour rate. Inactive, down or deleted providers stay in the order with the reason they are skipped. A route rule's HLR action (policy + optional subset of its customer trunks) wins over the trunk's HLR rules for that traffic (§13.24); the switch applies it at send time.
- **Credentials (§13.22)**: the provider password is write-only: never returned, logged as "(hidden)" in the change history and not undone.
- **Not built yet**: route rule conditions on other HLR results (not reachable, invalid number, error code, DNIS score; only "ported" exists), charging the HLR cost to the client (`consider_hlr_rate` on the trunk is in the schema), the HLR reports (§13.15, reports step) and the real HTTP lookups (backend).

## Number lists and Translation rules notes (build step 5.3)

- **Schema (migration 012)**: `translation_rules` gains `continue_after` (Is Continue; a trunk's own setting overrides it), Not Match flags for MCCMNC, text and both lists, `sender_conversion_list_id` (the Random / Sender ID Template list; `sender_list_id` is now only the Sender ID List match), content rewrite columns, `insert_at` (copied to the targets on save). `dlr_status_map` becomes an ordered list of `{fromStatus, fromError, toStatus, toError}`; old `{"UNKNOWN": "UNDELIV"}` maps were converted. `number_list_entries` gains `deleted_at` (delete archives, undo restores) and values are unique per list among live rows; 84 seeded duplicates were archived.
- **Engine (mock `routing/translate.ts`, same for the rule Test and the trunk Test)**: rules run in the trunk's order; a rule matches when every set condition holds (regex on sender, receiver and text, MCCMNC of the receiver by the "All" profile, a 3-digit code = the country; list membership; length guards; start / stop). A block ends the run; a matched rule set to Stop ends it too. A matching rule applies, in order: sender conversion, receiver conversion (the network is looked up again), TON / NPI, billing type, registered delivery, the first matching DLR conversion, content rewrite (Regex Index group or the whole match), then the MSG Template (`{text}` = the text so far). Regex Replace replaces every match of the pattern (JavaScript-style `$1..$9`; the Elixir backend should accept the same syntax). Random Number picks an entry; a template's `{n}` becomes one random digit each.
- **Number list values**: Random = 3-20 digits; Sender ID Template = up to 11 characters once `{n}` counts as one digit; Tag = 1-64 characters. Any list type can be a rule's Sender / Receiver ID List (decided 2026-10-17); a Sender ID Template entry matches with each `{n}` as one digit (`SHOP{n}{n}` matches `SHOP42`). The conversion list must fit the conversion.
- **Used by** counts live trunks reached through the targets; a trunk that switched the rule off is still listed (marked off). Editing a rule that touches more than one trunk asks for confirmation with the count. Duplicate to trunk makes an active copy that targets that trunk only and takes the original's place there (same position and Continue); the original is switched off on that trunk only and keeps running everywhere else. Undoing the duplicate archives the copy; the switch-off stays until changed on the trunk's Rules tab.
- **Not built**: rule sets saved as templates (§13.2, optional).

## Route map, Re-rating and QBR notes (build step 5.2)

- **Route map** (scope confirmed 2026-10-17): per customer trunk, every destination with a sell line in its rate tables, run through the live rules in order as a message without receiver or content (no warm-up, no number whitelists: the steady-state route). Same engine as Rate Lookup and the rule simulator. The mock computes a trunk's map in about 0.5 to 2 s and keeps it a minute; the backend should precompute it per trunk on rule and rate changes.
- **Routing speed-ups (mock)**: rules are indexed by destination code, rule time windows and vendor scopes are parsed once, and vendor costs per destination are cached a minute (cleared on rate changes and undo). A country-level code is now costed with each vendor's country line only, never a network's.
- **Re-rating**: EDRs billed with the request's rate table in the period (UTC days) are grouped by enterprise, destination, billed rate and hour and re-priced with the table's line valid at that time; a back-dated line counts from its stated date, which is how a back-dated RN rate is applied after all (§13.32). Billable units are `msg_count` where the EDR was billable. The difference per enterprise is a Reprocess note: customer, lower amount = credit note; vendor, lower cost = debit note. "No note" computes only. EDRs are never changed (§13.29). Requests are logged in the change history but not undone (maker-checker workflow). The mock runs the job in the background a moment after approval; the backend should use the job queue with progress.
- **QBR stats**: the window is the last 24 hours of EDRs (confirmed 2026-10-17). ADD = average delivery delay of delivered messages. A manual vendor stat wins until cleared; QBR rules order vendors by the destination's effective DLR, else the vendor's 7-day DLR.

## Product reference data notes (build step 5.1)

- **Imports** (§6.1 import modals) always run as a dry run first in the GUI; the same request with `dryRun: false` saves all or nothing, as one change that Undo reverses (rows added are archived again, rows changed get their old values, rows archived come back). Up to 200 errors, remarks and kept rows are listed. CSV may use commas or semicolons.
- **MCCMNC import, replace mode**: codes missing from the file are archived only when nothing uses them (open or scheduled rate lines, route rules, translation rules, live dial codes, MO numbers); the others are kept and listed. This is the "report codes that disappear but are still used" part of the 2026-10-16 MCC/MNC decision.
- **Safe delete** (§13.29): a product category is blocked while trunks, rate tables, route rules or translation / HLR rules use it; an MCCMNC code while rate lines, rules, dial codes or MO numbers use it (its 30-day traffic is shown, not blocking). Countries are not deleted. Restore is for administrators, as for other records.
- **Changing a code**: the MCC and MNC of a code in use cannot change (409), because rate lines, rules and dial codes refer to the code; network name, original MNC and country always can.
- **Number resolution** (Rate Lookup, route tests) uses the live prefixes of the default "All" profile only. Archived codes no longer appear in the destination search or as valid targets.
- **Fake data**: two extra profiles ("Ported numbers", "Short ranges") and 600 MO numbers (60 in the small profile), generated as the last step (`mock/src/generator/masterData.ts`) so the rest of the seed is unchanged.

## Open questions

- **Redis memory for messages in flight (2026-10-24, backend step 4).** To match receipts, the switch keeps each sent
  message in Redis (about 0.75 KB with its index keys) until the vendor trunk's DLR timeout plus an hour; the default
  DLR timeout is 48 h. At 50 million messages a day that is about 100 million messages held, roughly **75 GB of Redis
  memory**, more than the servers should give it. Options: (a) keep messages in Redis for a shorter time (e.g. 6 h,
  about 10 GB at that volume) and match later receipts from the ClickHouse EDRs instead (slower, but rare); (b) keep
  48 h and size Redis for it; (c) shorten vendor DLR timeouts. Proposal: (a). Built for now: the full DLR timeout.

- **Vendor TLS certificates (2026-10-24, backend step 3).** Should the switch check a vendor's TLS certificate
  (trusted CA and matching host name) before binding? Checking protects the vendor password from a man-in-the-middle,
  but a vendor with a self-signed certificate then cannot bind. Built: checked by default (`VENDOR_TLS_VERIFY=peer`),
  `none` switches it off for every vendor. Proposal: keep checking by default and, if some vendors use self-signed
  certificates, add a per-trunk "Skip certificate check" option (the trunk's "SSL File" field could hold the vendor's
  own certificate instead).
